# Deploying Pigeon Mail

Pigeon is one Rust binary (`pigeon`) with two subcommands: `serve` (everything in
one process — API, MCP, web, SMTP in/out) and `mcp` (stdio MCP server). Pick the
deployment style that matches your host:

| Style | Use it for | Files |
|---|---|---|
| Docker | one container, quickest look | `Dockerfile`, `.dockerignore` |
| Compose | one VPS, restart on boot | `docker-compose.yml`, `.env.example` |
| systemd | bare-metal VPS, no container runtime | `install.sh` |
| Kubernetes | multi-tier / managed clusters | `deploy/k8s/` (skeleton) |

> **Note:** the `pigeon` binary (`serve` / `keygen` / `mcp`) ships in this
> repository — build it with `make build` or let `install.sh --bin` install a
> prebuilt one.

## Ports and volumes

| Port | Purpose | Exposure |
|---|---|---|
| 8000 | HTTP API + MCP-over-HTTP, `/healthz`, `/readyz` | behind a TLS terminator |
| 25 | inbound SMTP from remote MX | must be reachable from the internet |
| 587 | submission with AUTH | reachable from your clients |

| Path | Content | Notes |
|---|---|---|
| `/var/lib/pigeon` | `pigeon.db` (SQLite, WAL) | real disk, never tmpfs; back it up |
| `/etc/pigeon/master.key` | 32-byte master key, 64 hex chars | `0640 root:pigeon`; back it up |

Configuration is 12-factor: every knob is a `PIGEON_*` environment variable
(reference: `.env.example`, source of truth: [ARCHITECTURE.md](ARCHITECTURE.md)).

## Before you deploy

1. **A host with port 25 free.** See [DNS records](#dns-records) — this is the
   requirement that surprises people.
2. **A TLS terminator** in front of `:8000` (Caddy, nginx, Traefik, a cloud LB).
   Pigeon serves plain HTTP internally; it does not terminate public TLS itself.
3. **A master key.** Generated by `install.sh` or by you for Docker; see
   [Master key rules](#master-key-rules).

## Docker: one-liner

```bash
mkdir -p secrets
openssl rand -hex 32 > secrets/master.key        # 64 hex chars = 32 bytes
sudo chown root:10001 secrets/master.key          # container runs as uid/gid 10001
sudo chmod 640 secrets/master.key

docker run -d --name pigeon \
  --restart unless-stopped \
  -p 8000:8000 -p 25:25 -p 587:587 \
  -v pigeon-data:/var/lib/pigeon \
  -v "$PWD/secrets:/etc/pigeon:ro" \
  -e PIGEON_HTTP_ADDR=:8000 \
  -e PIGEON_SMTP_IN_ADDR=:25 \
  -e PIGEON_LOG=info,json \
  pigeon-mail:local
```

Build the image first — `docker build -t pigeon-mail:local .` — and add
`--target pigeon-webmail --build-arg WITH_WEBMAIL=1` to ship the optional webmail
bundle. The default target never pulls a Node image, so the off-switch really is
off.

No `HEALTHCHECK` is defined: the runtime image is distroless (no shell, no curl).
Probe `/healthz` and `/readyz` from outside until the binary ships a built-in
probe.

## Compose

```bash
cp .env.example .env
mkdir -p secrets && openssl rand -hex 32 > secrets/master.key
sudo chown root:10001 secrets/master.key && sudo chmod 640 secrets/master.key
docker compose up -d --build
docker compose logs -f pigeon
```

The optional webmail bundle needs **two** variables because they do different
jobs: `WEBMAIL_TARGET=pigeon-webmail` selects the Dockerfile target (the only way
to reach the Node stage) and `WITH_WEBMAIL=1` is what that stage builds.

```bash
WEBMAIL_TARGET=pigeon-webmail WITH_WEBMAIL=1 docker compose up -d --build
```

Leaving both unset (or `WITH_WEBMAIL=0`) renders no build target at all — the
binary-only image, no Node image pulled. `.env` is optional: without it the
container runs on the image defaults, which already match
[ARCHITECTURE.md](ARCHITECTURE.md).

`:25` must be free on the host or another MTA already answering there will
conflict — use a dedicated IP or `network_mode: host` on a host that runs nothing
else. Full comments live in `docker-compose.yml`.

## systemd: `install.sh`

```bash
sudo ./install.sh --domain example.com
```

`--domain` is the **mail domain you serve** (`example.com`), not the SMTP host
(`mail.example.com`): MX, SPF, DKIM and DMARC are published on that domain.

Useful flags: `--port <api-port>` (default 8000), `--data-dir <path>` (default
`/var/lib/pigeon`), `--bin <path>` (install a locally built binary instead of
downloading), `--no-webmail`, `--no-start`.

What it performs, in order:

1. checks the OS is Linux and maps the arch (`x86_64` → `amd64`,
   `aarch64` → `arm64`);
2. creates the `pigeon` system user (no login shell, home = data dir);
3. creates `<data-dir>` (`0750 pigeon:pigeon` — the service writes there) and
   `/etc/pigeon` (`0750 root:pigeon` — the group needs traverse access, otherwise
   the service cannot read `master.key` even at `0640`);
4. creates `/etc/pigeon/master.key` **only if missing** (`0640 root:pigeon`) —
   an existing key is never regenerated;
5. installs `pigeon` to `/usr/local/bin` — either `--bin <path>` or
   `pigeon-<arch>.tar.gz` from the latest GitHub release (a 404 means no release
   exists yet: build from source and pass `--bin`);
6. best-effort `setcap cap_net_bind_service=+ep` so `:25`/`:587` bind as
   non-root;
7. writes `/etc/pigeon/pigeon.env` and `/etc/systemd/system/pigeon.service`
   (`User=pigeon`, `AmbientCapabilities=cap_net_bind_service`,
   `ProtectSystem=strict`, `ReadWritePaths=<data-dir>`, `Restart=on-failure`);
8. unless `--no-start`: `systemctl daemon-reload`, then `enable --now` — or
   `restart` when the unit is already active, which is what makes a re-run
   (binary upgrade, new env) actually take effect;
9. prints the DNS records, the API-key call and the webhook pointer.

The installer is idempotent: re-running upgrades the binary, restarts an active
service, and leaves the master key and database alone.

## DNS records

An MX record is a promise that something answers on **port 25**. Publishing MX
without a reachable `:25` silently blackholes inbound mail — no bounce, no log.

> **Warning — `:25` ownership.** On a server that already runs another MTA
> (postfix, exim, mailcow, mail-in-a-box…), Pigeon inbound cannot share `:25`.
> You need **its own IP address**, or you must **take over `:25`** by stopping
> the other MTA. Submission (587, inbound listener) and the API (8000) are
> unaffected.

One model, one place. Every record lives on the **mail domain you serve**
(`example.com`); the only thing published on `mail.example.com` is the address
record of the machine that answers `:25`.

| Published on | Type | Value | Notes |
|---|---|---|---|
| `mail.example.com` | A | `<server-public-ip>` | the host that answers `:25`; PTR should match; add `AAAA` for IPv6 |
| `example.com` | MX (10) | `mail.example.com.` | points the whole domain at that host — not at itself |
| `example.com` | TXT | `v=spf1 a mx -all` | SPF belongs on the domain, never on the host |
| `<selector>._domainkey.example.com` | TXT | `v=DKIM1; k=rsa; p=<public-key>` | DKIM selector lives under the domain |
| `_dmarc.example.com` | TXT | `v=DMARC1; p=quarantine; rua=mailto:dmarc@example.com` | DMARC at `_dmarc.<domain>`; start with `p=none` while testing |

Publishing these on `mail.example.com` instead — an MX pointing at itself, SPF
on the host, DKIM under the host name — is the classic self-hosted mistake: the
records exist, but no receiver reads them. Mail is judged on the domain in the
address, not on the MX host name.

Notes:

- Replace every `example.com` and `<…>` with your values.
- `-all` in SPF is deliberate: a self-hosted mail server that sends only its own
  mail should fail everything else. Soften to `~all` while you migrate.
- Keep TXT records under 255 characters per string; DKIM keys are usually split
  into two quoted chunks — DNS providers handle that automatically.
- Reverse DNS (PTR) of the sending IP should resolve to `mail.example.com`, or
  large receivers will reject you regardless of SPF/DKIM/DMARC.
- Verify after publishing — same names, same place as the table:

```bash
dig +short A mail.example.com
dig +short MX example.com
dig +short TXT example.com
dig +short TXT _dmarc.example.com
dig +short TXT <selector>._domainkey.example.com
```

## Master key rules

The key is the only thing that makes stored mail readable (ADR 0003). There is
no recovery path and no support override:

- **Never commit it.** Not in git, not in an image, not in a ConfigMap.
- **Permissions:** `0640`, owner `root`, group `pigeon` (uid/gid `10001` in
  containers). The service only needs to read it.
- **One file, one variable:** `PIGEON_MASTER_KEY_FILE` points at it. The key
  value is never an env var.
- **Back up key + database together.** A database without the key is noise; a key
  without the database only lets you start an empty instance. Keep both in the
  same backup set, encrypted, off-host.
- **Losing the key = losing the mail.** Rotation is not supported.
- **Never regenerate it on an existing install.** `install.sh` skips key
  creation when the file exists; keep it that way.

## After deploy

1. `curl -fsS http://127.0.0.1:8000/healthz` → liveness, `.../readyz` →
   store reachable + key present.
2. Create the first API key: `POST /v1/account/keys` with `{"name":"first","scopes":
   ["full"]}` (scope `full` — key administration is itself a `full` operation); the
   `pk_…` token is shown once.
3. Register a webhook (`POST /v1/webhooks`) to receive HMAC-signed delivery
   events.
4. Send a test message through `/v1/emails` and check the events trail:
   `queued → sent | deferred | bounced`.
